# SomenのPR作成

一つの目的を一つのPRにする。テスト・文書・その機能を示すデモは同じ目的に含め、開発運用の変更は機能追加から分ける。

## 名前と説明

- ブランチは `feat/grouped-flow-diagrams`、`fix/paused-resize`、`ci/issue-triage` のように `type/short-topic` とする。Conventional Commits自体はブランチの規格ではないため、同じtypeを使う運用とする。
- コミットはConventional Commits形式の簡潔な英語。PRタイトルも `feat: 条件をたどれるフロー図を作れるようにする` のように目的を短く示す。長くなる説明は本文へ移す。
- 本文は日本語で、利用者の課題と得られる結果を先に書く。UIやAPIなら「何が作れるか」「何の指定を省けるか」を伝える。
- diffからすぐ読める追加属性・関数・ファイルの列挙は省く。互換性やトレードオフを判断するのに必要な実装詳細だけ残す。
- 検証は実行結果を根拠に短く書き、未実施・失敗・CI待ちを成功と混ぜない。テンプレートに合わせるための空の節は作らない。

## 検証とレビュー

AGENTS.mdの関連チェックを実行する。レビューは実装を担当していない独立したエージェントに依頼し、現在の差分と周辺コードから不具合・互換性・テスト不足を確認する。指摘を修正したら、影響するチェックとレビューを更新する。

UI変更はローカルのsandboxまたはpreviewを起動し、広い画面と320px幅で実際に見る。今回の変更を再現する操作も確認する。スクリーンショットを撮るだけで目視確認済みとしない。独立したレビューにも実画像を渡して文字切れや重なりを確認してもらう。操作は操作記録、読み上げはアクセシビリティ情報や実際の読み上げを別の根拠とし、画像だけで確認済みとしない。

画像やHTMLレポートはGitHub添付かCI artifactとしてPRから辿れる形にする。生成画像やレポートをコードのブランチにコミットしない。外部PRでは使えないlocalhostリンクだけを証跡にしない。

## 公開と完了確認

作成・pushが依頼済みなら、その範囲で目的別にステージしてコミットし、正しいremote・base・headでPRを作る。独立した変更はmainから別ブランチにする。依存がある場合だけ依存関係を本文に書く。

リモートでしか検証できない項目が残る場合はDraft PRを作り、CI待ち・未検証を本文に明記して実行を確認する。

作成後はbase/head/SHA・タイトル・本文・ファイル一覧・CIを取得して確認する。Codexアプリから作成した場合はPRをチャットに添付する。

通常のPRはレビュー待ちにし、作成依頼をマージ許可と解釈しない。Auto Approvalはリポジトリの自動化ポリシー（`.github/automation-policy.md`）が存在し、その条件に適合する変更だけに使う。ポリシーが未導入なら付与しない。ラベルだけでレビューやCIを代替せず、保護ルールを迂回しない。パッケージ公開・deploy・ライセンス変更は別の指示を必要とする。

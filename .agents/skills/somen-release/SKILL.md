# Somen release

[リリース方針](../../../.github/releasing.md)を読み、現在のmain、公開済みバージョン、未公開の利用者向け変更を確認する。

- CI・開発用依存だけの変更は通常ノートに載せず、公開もしない。実行時依存・互換性・セキュリティ対応は利用者への影響で判断する。
- PRの差分を確認し、必要なら `release:include` / `release:security` / `release:breaking` を付ける。ラベル名だけで掲載・除外を決めない。
- 次のバージョンは既存の公開チャンネルを維持する。alphaから安定版への移行を推測しない。
- バージョン更新は目的を分けたPRにし、前提PR、利用者に届く変更、検証結果を書く。`Auto Approval` にしない。
- 公開はバージョンPRのレビュー・mainへのマージ・そのコミットのCIとCodeQL成功後にRelease workflowで行う。先にローカルからタグを作成したりnpm publishしたりしない。
- 生成ノートを公開前にプレビューし、公開後はnpmのバージョンとチャンネル、GitHub Releaseを確認する。公開予定、CI成功、実際の公開完了を区別して報告する。
- 失敗時は既存タグ・npm・Releaseの状態を確認してから既存workflowを再実行する。タグや公開済みパッケージを上書きしない。
